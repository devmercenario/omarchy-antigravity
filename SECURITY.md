# Security Policy

## Overview

The `omarchy-antigravity` plugin integrates the Google Antigravity CLI (`agy`) with Omarchy Linux.
Security and defense-in-depth are primary architectural priorities:

- **Strict User-Space Containment**: All plugin binaries, caches, and state files operate exclusively inside standard user directories (`~/.local/bin`, `~/.config/omarchy`, `~/.cache/omarchy`, `~/.local/state/omarchy`). No system files (`/etc`, `/usr`, `/root`) are modified or accessed.
- **Zero Elevated Privileges**: The plugin never invokes `sudo`, `su`, `pkexec`, or any privilege-escalation mechanism.
- **No Private Key Access**: The plugin has zero access to SSH keys (`~/.ssh`), GPG keys (`~/.gnupg`), or system keyrings outside its designated secret service domain (`service: gemini, username: antigravity`).
- **Standard Permission Model**: The plugin executes `agy` using its standard interactive permission confirmation model. No permission bypass flags (`--dangerously-skip-permissions`) are used or distributed, and the plugin never switches the user to a launch that uses one: on Omarchy 4.5, whose own `agy` default agent launches with that flag, the plugin's `antigravity` default (and its launcher) stays as it is unless the user chooses otherwise.
- **Non-Conflicting Namespace**: Plugin-specific executables use explicit prefixes (`omarchy-antigravity*`). Two intentional exceptions shadow stock Omarchy commands on `PATH`: `omarchy-agent-usage-update` (the installer backs up any prior copy and the uninstaller restores or removes it so the stock helper is never permanently masked) and `omarchy-agent`, a thin launcher that only handles the `antigravity` default agent (opening `agy` with its standard permission prompts, never a bypass) and `exec`s Omarchy's stock launcher unchanged for every other agent. The installer never replaces an `omarchy-agent` it did not write (no plugin marker), and the uninstaller removes only the plugin's copy. On Omarchy 4.5 and later, which support Antigravity natively, the updater copy is not installed and `omarchy-antigravity adopt-native` (run by the installer, and once by the post-update hook) removes the plugin's marked copy, so 4.5's updater is never shadowed; the launcher stays, since it is what keeps the plugin's `antigravity` default opening `agy` with permission prompts.

## Credential & Data Protection Architecture

### 1. Descriptor-Level Token Verification (Anti-Symlink & TOCTOU Defense)
When reading authentication tokens from `~/.gemini/antigravity-cli/antigravity-oauth-token`:
- Opened with `os.O_RDONLY | O_NOFOLLOW | O_CLOEXEC` to strictly prevent symlink traversal.
- File metadata is inspected directly on the open descriptor via `fstat(fd)`.
- Rejects non-regular files (`stat.S_ISREG`), UID mismatches (`st.st_uid != os.getuid()`), and permissive permissions (`(st.st_mode & 0o077) != 0`). Only owner-private files (`0600` or `0400`) are accepted.
- Enforces a strict 64 KiB size limit prior to in-memory decoding and JSON parsing.

### 2. Atomic & Private File Writing
All state, cache, and token files are created using atomic publish semantics:
- Temporary files are created in the target directory using `tempfile.mkstemp` with `O_CREAT | O_EXCL` and mode `0600`.
- Data is flushed and committed using `os.fsync(fd)` before closing the descriptor.
- Published via `os.replace`, ensuring atomic replacement on POSIX filesystems and safely replacing any existing symlinks without following them.

### 3. Native / Installed Application OAuth Model
In accordance with [RFC 8252 (OAuth 2.0 for Native Apps)](https://tools.ietf.org/html/rfc8252), desktop and installed CLI clients cannot protect client secrets:
- Google's OAuth 2.0 architecture treats native client secrets as non-confidential application identifiers.
- User authorization tokens (access/refresh tokens) are stored privately (`0600`) in user space or the system Secret Service keyring (`libsecret`).
- **agy's credentials are read-only to the plugin.** The collector reads `antigravity-oauth-token` (or the keyring entry) but never writes either back. When agy's own access token is stale, the collector mints one for itself and keeps it in its own `0600` cache (`~/.cache/omarchy/agent-usage/antigravity-access-token.json`, keyed by a SHA-256 fingerprint of the refresh token — the refresh token itself is never copied), so it can never race or corrupt the CLI's own token refresh.
- Client credentials can be overridden anytime via environment variables:
  - `ANTIGRAVITY_CLIENT_ID`
  - `ANTIGRAVITY_CLIENT_SECRET`
- **Strict mode (opt-in):** set `ANTIGRAVITY_STRICT_CLIENT=1` together with both variables to refuse token refresh whenever explicit credentials are absent. In strict mode the collector never falls back to the built-in default client and instead reports the requirement, so a deployment can avoid the embedded installed-application identifier entirely.

### 4. Network Security
- All remote API endpoints exclusively use TLS (`https://`).
- Every network request enforces strict socket timeouts (5s to 10s), and every request, body read and helper is further cut to a 40-second budget for the whole run (the body loop checks it between reads, so a trickling server cannot stretch a read past it). DNS lookups, connects, TLS handshakes and a trickled status line block in C where neither a timeout nor a signal handler reaches, so a watchdog ends any run still going at 50 seconds: it kills the helpers, prints a `Quota unavailable` record saying the run ran out of time, and exits — always inside the updater's `timeout 60`. Authentication and other 4xx errors (except 408/429) are not retried, and a request that cannot even be built (say, a malformed token) fails without retrying and without echoing its contents.
- **Bounded response reads.** Every HTTP body — including `HTTPError` error bodies — is read through a single `read_bounded()` helper that checks `Content-Length` when present and never reads more than the endpoint ceiling plus one byte. This prevents a compromised or misbehaving endpoint from forcing unbounded allocation. Conservative per-endpoint ceilings are applied: 16 KiB for OAuth token refresh, 16 KiB for Google userinfo, 64 KiB for the plan lookup (`loadCodeAssist`), 256 KiB for the quota summary, and 4 KiB for error diagnostics.
- **Redirects refused.** A process-wide no-redirect opener rejects every HTTP redirect, so a credential-bearing request (OAuth client secret + refresh token, or a quota bearer token) can never be replayed to an attacker-chosen host.
- No third-party trackers, telemetry, or analytics are included.

### 5. Bounded Local JSON Reads
The collector's cache and state JSON files (`antigravity-limits.json`, `antigravity-agy-usage.json`, `antigravity-access-token.json`, `antigravity-account.json`, `antigravity-groups.json`, `antigravity-alert.json`, `antigravity-history.json`) are read through the same no-follow descriptor discipline used for the OAuth token, with a 1 MiB ceiling enforced before any decoding or JSON parsing. The access-token cache must also be private (`0600`), or it is ignored and a fresh token minted; the cache directory must belong to the user and end up `0700`, or the run reports `Collector error` instead of writing there. Cache writes are capped at 1 MiB. Credentials or caches holding valid JSON of the wrong shape (non-objects, non-finite or huge numbers, oversized group lists) are treated as cache misses instead of crashing the collector, and any unexpected error still produces a record (`Collector error`) so the panel never silently freezes on stale numbers. Only one record is ever printed per run. Collector runs (the bar's updater, `omarchy-antigravity status`, a manual run) are serialized by a private run lock, so they never race on these files. The CLI history file (`~/.gemini/antigravity-cli/history.jsonl`) is opened with `O_NOFOLLOW`, must be a regular file owned by the current user, and is ignored entirely above a 16 MiB ceiling before it is streamed.

### 6. Bounded Helper Output
Helper processes that feed credential or quota state (`secret-tool`, `agy -p /usage`, and `notify-send`) are executed with a hard timeout, and the first two with a 512 KiB stdout ceiling. A helper that exceeds either bound is terminated and treated as a failure, so it cannot force unbounded allocation or hang the collector. Helpers run in their own process group, registered for cleanup in one step (a signal arriving while one starts is held until it is tracked; blocking signals instead would leak the blocked mask into agy through exec). `SIGTERM`, `SIGINT`, `SIGHUP` and `SIGQUIT` all kill every tracked group before the collector exits, so Ctrl-C or closing the terminal during `omarchy-antigravity status` leaves no agy or MCP server behind. Once a helper exits (or is killed), whatever is left of its group is killed too, while the exited helper is still unreaped so the group id cannot have been reused; the group stays tracked until its output is drained, and the pipe is only closed after the reader thread is done, so a descendant holding the pipe open can neither stall the collector past its deadline nor outlive it. `pgrep` and `notify-send` are also cut to the remaining budget. Desktop notification bodies are escaped, since notification daemons render them as Pango markup, and every text that reaches the panel, a notification or the log (HTTP error reasons and bodies, a refused redirect's URL, exception messages) is stripped of control characters and length-capped. Parsed quota is capped at 32 limit entries with short, control-character-free names, so a response inside the byte ceilings cannot become a multi-megabyte record or cache, and the panel lays out at most 32 rows. The Antigravity status line additionally bounds stdin to 256 KiB. The usage-update helper wraps every collector in `timeout --kill-after=5 60` (SIGKILL for one that ignores or outlives the TERM), reads at most a 4 MiB record and the first 64 KiB of a collector's stderr (50 lines of at most 500 characters reach the log), and removes its temp files even when a refresh is interrupted.

**`agy -p /usage` and MCP servers.** The quota API stopped reporting the Gemini pools, so the collector reads them from `agy -p /usage`. Every such call starts the MCP servers configured in agy (for the call's few seconds, inside the killed-on-exit process group). It happens only while an agy session is already running, at most once every 10 minutes (the answer is cached), and on an explicit `--force` refresh. A call that timed out is never cached, so a slow moment does not hide the Gemini pools for 10 minutes.

### 6b. Trusted Helper Resolution
In the Python collector, `agy`, `secret-tool`, `pgrep`, and `notify-send` are resolved to an absolute path and rejected unless the binary is an executable regular file owned by root or the current user, and neither it nor any ancestor directory is writable by others: world-writable is always refused, and group-writable only passes for the user's own files in their private group (umask-002 setups). A poisoned `PATH` entry therefore cannot silently substitute an attacker-controlled helper. The shell scripts (installer, CLI helper, status line, updater) resolve `agy`, `jq`, `git`, and `secret-tool` through `PATH` like any other user command, so they trust the user's `PATH`. The status line additionally probes only loopback addresses, so a configured endpoint cannot be used to probe arbitrary hosts, and it treats the JSON agy sends on stdin as untrusted: the width must be a plain number before it reaches shell arithmetic, and folder and branch names are stripped of control characters and printed with `%s` (no terminal escape injection).

**Untrusted repositories.** The status line renders inside whatever directory agy runs in, including an extracted archive or a fresh clone. `git status` re-reads files whose stat data changed and runs them through any clean filter the repository configures, which would execute that repository's commands. So when the repository's own config (local or worktree scope) defines `filter.*`, the status line shows only what needs no file contents (branch via `symbolic-ref`/`rev-parse`, staged changes via `diff-index --cached`, untracked files via `ls-files --others`); filters from the user's own global or system config (git-lfs) are trusted. Every git call runs with `GIT_OPTIONAL_LOCKS=0` (it never writes `.git/index`, so no `index.lock` races with the agent's own commits), `core.fsmonitor` disabled, submodules ignored, a 2-second timeout (a huge or network-mounted repository cannot stack hung processes) and a 1 MiB output cap.

### 7. Installation, Removal, and User Consent
The installer and uninstaller never destroy user data:
- `shell.json`, the agy `settings.json`, and the default-agent file get a timestamped backup (mode kept, never overwriting an earlier one taken the same second) only when a change is actually written, and only the 3 newest backups of each are kept. A config kept as a symlink (stow, chezmoi) stays one: changes are written to the file it points at.
- A pre-existing Antigravity CLI `statusline.sh` and `omarchy-agent-usage-update` are backed up once (single-slot `.bak`); the update-helper backup is a hidden dotfile so the collector-discovery glob can never mistake it for a collector. A helper of the user's own met when that slot is already taken goes to the backup folder below instead, and a user's own old visible `omarchy-agent-usage-update.bak` is left where it is.
- The plugin's own files carry a marker line (`# omarchy-antigravity: ...`), and the installer records the SHA-256 of every file it installs (`~/.config/omarchy/antigravity.installed`). Before a plugin file is replaced (reinstall) or removed (uninstall, Omarchy 4.5 hand-over), a copy edited since install — or, without a record, one that differs from the shipped copy — is kept in `~/.local/share/omarchy-antigravity/backups/` (outside `PATH` and the collector glob; never deleted by the uninstaller). A reinstall never backs up the plugin's own unedited copy as if it were the user's.
- Plugin UI files (`Panel.qml`, `Main.qml`, and assets in the user's agents plugin folder): the pre-install file is kept as `.bak`; edits made after an install get timestamped backups before a reinstall replaces them or the uninstaller restores the `.bak`.
- A `statusLine` entry of the user's own (pointing anywhere but the plugin's script) is kept aside privately (`statusline.omarchy-antigravity.previous.json`, `0600`) before install replaces it, and put back by the uninstaller.
- Config files are rewritten through a temporary file next to the real file (atomic `mv`, original mode kept), and only when the JSON content changes, so the bar's file watcher never sees a partial `shell.json` and an unchanged file keeps its inode and mtime.
- The installer refuses to write plugin binaries through an existing symlink, and copies use `--remove-destination` so symlinks are replaced rather than followed.
- **Default agent.** The plugin sets the default agent only with consent and touches its opt-in marker right after; the default counts as the plugin's only while the agent file is not newer than the marker and holds a value the plugin writes. Any later choice of the user's own (including Omarchy's own Gemini or 4.5's `agy`) is never overwritten by the post-update hook or reverted by the uninstaller. The legacy `~/.local/bin/gemini` shim from early releases is removed only when the file is exactly that shim.
- The uninstaller only undoes what is recognizably the plugin's: the status line and its `statusLine` entry only when the script carries the marker and the entry points at it; `providers.antigravity` only when it is exactly `{"enabled": true}`; the agents plugin folder only when the installer created it (marker file), through `omarchy-plugin-remove` or, without it, by moving the folder aside (`.<id>.bak.<n>`) and pointing the bar back at Omarchy's widget. It restores the shadowed update helper, agent selection, and UI files, and deletes the collector's `antigravity-*` caches (including its private access-token cache) and the updater's leftovers in the state directory.
- **Omarchy 4.5 hand-over.** `omarchy-antigravity adopt-native` removes the plugin's collector, its record and its updater copy (edited copies are kept, as above), and switches only the `<user>.agents` widget the plugin installed (with a single `shell.json` backup) back to Omarchy's. It never changes the default agent or removes the launcher. The post-update hook runs it once (recorded in `~/.config/omarchy/antigravity.native-adopted`) and reports it with a desktop notification, so a later choice of the user's own — going back to the plugin's panel, say — is never undone by the next update.
- The usage updater refuses to recurse (an environment guard, plus skipping any discovered id starting with `update` and any id that is not a plain lowercase name), runs collectors in parallel, takes a per-collector lock so overlapping refreshes (bar timers, a systemd timer, the plugin service) never run one collector twice, and reports collector failures on stderr with a non-zero exit instead of silently keeping stale records.
- The post-update hook only fills in a **missing** antigravity provider preference; an explicit `providers.antigravity.enabled = false` is left untouched.

### 8. Shell Plugin Data Hardening
Data derived from synced snapshots is aggregated into null-prototype maps, so an untrusted key such as `__proto__` becomes an ordinary own property instead of mutating an object prototype in the Quickshell runtime. Synced snapshot values are coerced through `String()`/numeric helpers before use. Because the sync folder is shared and parsed on the GUI thread, the scan skips snapshots larger than 1 MiB, reads at most 64 of them, and merges at most 16 agents; paths and limits reach the scan script as argv, never interpolated into it. Agent ids from synced snapshots or records must match `^[a-z0-9][a-z0-9-]{0,63}$` before they become tabs, icon paths or command arguments (so an id cannot point the icon loader at an arbitrary local file), and the retry list is built from record file names, not their contents. Commands the panel runs (`bar.run()`, `Process`) are constant strings or argv arrays and never include data read from records.

## Reporting a Vulnerability

If you discover a security vulnerability within this project, please report it responsibly:

1. Do **not** open a public issue.
2. Submit a report through GitHub Private Vulnerability Reporting on this repository.
3. Include detailed reproduction steps, affected environment, and impact assessment.

We appreciate your assistance in keeping the Omarchy ecosystem safe!
